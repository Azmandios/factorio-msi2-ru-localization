# Модель релиза и версионирования

Единые правила версионирования, тегов и коммитов для мода-перевода
`msi2-ru-localization`.

## Принцип

Версия мода-перевода — независимый semver (`MAJOR.MINOR.PATCH`), который описывает
**сам перевод**, а не версию оригинала. Совместимость с оригиналом отслеживается
отдельно (см. «Совместимость с MSI2»).

Источник версии — поле `version` в `info.json` (единственный источник истины,
как и в остальных модах проекта). Git-теги и zip-архивы выводятся из него.

## Версии (semver)

| Bump | Что означает для мода-перевода |
|------|--------------------------------|
| **PATCH** (`0.1.0` → `0.1.1`) | Исправления перевода (опечатки, терминология), фиксы инструментов/сборки, документация. Без новых строк. |
| **MINOR** (`0.1.0` → `0.2.0`) | Новый переведённый контент: новые ключи, перевод нового мода, перенос под новую минорную версию MSI2. Обратная совместимость сохраняется. |
| **MAJOR** (`0.1.0` → `1.0.0`) | Стабильный релиз или ломающее изменение (структура мода, отказ от поддержки, смена схемы версий). |

Правило: пока в игре не пройден ручной визуальный QA — держим `0.x.y`. После
подтверждения качества первым стабильным релизом ставим `1.0.0`.

## Совместимость с MSI2

Наш мод жёстко зависит от `Mining-Space-Industries-II >= 1.0.4`. Текущий перевод
покрывает **MSI2 1.0.4** и его зависимости в актуальных на момент релиза версиях
(`factorio-crash-site` 2.1.0, `mferrari_lib` 0.7.8, `Rocket-Silo-Construction` 2.1.3).

При выходе новой версии MSI2:

1. `make sync-source` — переснять английские исходники (появятся новые/изменённые ключи).
2. `make report --missing` — увидеть, что доперевести.
3. Доперевести строки, `make check && make smoke`.
4. Поднять нижнюю границу зависимости в `info.json` (`>= 1.0.x`).
5. Релиз с bump **minor**.

Точное соответствие «версия перевода ↔ версия MSI2» фиксируется в `changelog.txt`.

## Теги (semver)

- Формат: `v<version>`, где `<version>` — значение `info.json`.
- Тег аннотированный: `git tag -a v0.1.0 -m "Release v0.1.0"`.
- Тег ставится на коммит релиза (после bump версии и записи в changelog).
- Теги не удаляются и не пересоздаются; при ошибке релиза — новый patch-релиз.

## План коммитов (conventional commits)

Один коммит — одно логическое изменение. Типы коммитов и их влияние на версию:

| Тип | Назначение | Bump |
|-----|------------|------|
| `feat(locale)` | новый переведённый контент, новый мод | minor |
| `fix(locale)` | исправление перевода | patch |
| `chore` / `build` | инструменты, сборка, Makefile | patch |
| `docs` | README, docs, changelog | patch |
| `test` | smoke/check-скрипты, отчёты QA | patch |
| `feat!` / `BREAKING CHANGE` | ломающее изменение | major |

Примеры:

```
feat(locale): перевод технологий MSI2
fix(locale): унифицировать термин «исследовательский пакет»
chore(release): v0.1.1
```

Релизный коммит оформляется как `chore(release): vX.Y.Z` — он только меняет версию
в `info.json` и добавляет запись в `changelog.txt`.

## Процесс релиза

Автоматически через `make release`:

```bash
make release BUMP=patch CHANGES="Исправить термин «исследовательский пакет»"
# или BUMP=minor / BUMP=major / BUMP=0.2.3 (явная версия)
```

Скрипт `scripts/release.sh`:

1. Считает текущую версию из `info.json`, вычисляет новую.
2. Обновляет `info.json`.
3. Дописывает блок в `changelog.txt` (версия, дата, список изменений).
4. Коммитит: `chore(release): vX.Y.Z`.
5. Ставит аннотированный тег `vX.Y.Z`.
6. Собирает zip: `make build`.

Затем публикация:

```bash
git push origin main
git push origin --tags
```

## Публикация на Mod Portal

Локальный релиз (git-тег + zip) и публикация на [mods.factorio.com](https://mods.factorio.com)
разнесены на два шага.

**Одноразовая подготовка:**

1. Создать страницу мода `msi2-ru-localization` на портале через веб-интерфейс
   (название, описание, лицензия, иконка). **API умеет только добавлять релизы,
   но не создавать мод** — это делается вручную в браузере.
2. Получить API-токен с правом «ModPortal: Upload Mods» на https://factorio.com/profile.
3. Сохранить токен локально (не в git!):

   ```bash
   printf '%s' '<username>.<key>' > .mod-portal-token && chmod 600 .mod-portal-token
   # либо экспортировать переменную окружения:
   export MOD_PORTAL_TOKEN='<username>.<key>'
   ```

**Публикация релиза:**

```bash
make publish
```

Скрипт `scripts/publish.sh` собирает zip, запрашивает pre-signed URL у
`init_upload` и загружает архив на портал. Файл `.mod-portal-token` — в
`.gitignore`, чтобы токен не попадал в репозиторий.

Ручной вариант (без скрипта) описан в том же порядке ниже в разделе «Вручную».

## Вручную (пошагово)

1. Правки перевода в `locale/ru/*.cfg`, коммит `fix(locale)` / `feat(locale)`.
2. `python3 -c "import json;print(json.load(open('info.json'))['version'])"` — узнать текущую.
3. Обновить `info.json` → новая версия; добавить блок в `changelog.txt`.
4. `git add info.json changelog.txt && git commit -m "chore(release): v<новая>"`.
5. `git tag -a v<новая> -m "Release v<новая>"`.
6. `make build`, затем `git push origin main && git push origin --tags`.
